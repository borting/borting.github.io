Changes to memory ordering are made both by the compiler (at compile time) and by the processor (at run time), all in the name of making your code run faster.

The cardinal rule of memory reordering: `Thou shalt not modify the behavior of a single-threaded program.`

The cardinal rule of OoOE is that you don't break single-threaded programs.

All about SMP and shared memory.

A processor never sees its own memory effects out of order, even when threads are pre-empted and scheduled at arbitrary times.

# Reordering

Both compiler and processor might reorder the logic of the source code.
```
Source code -- Compiler Reordering --> Machine Code --> Processor Reordering --> Memory
```

Memory Model of the hardware (i.e processor families) determines how a processor can reorder the execution of machine code.


# Memory Reordering

Four basic types of memory dependence ([Ref,](https://preshing.com/20120710/memory-barriers-are-like-source-control-operations/)):
* LoadLoad
* StoreStore
* LoadStore
* StoreLoad

If no barriers, ordering is defined by dependencies:
	* Address: value returned by a read is used to compute the address of a subsequent write
	* Control: value returned by a read is used to determine the condition flags (e.g. Z flag of arm) and the flags determines the address of a subequent access
	* Data: value returned by a read is used as data written by a subsequent write (LoadStore)
	* Read after read
	* Store speculation

Control dependency does not force ordering.

Different memory models allow processors to do different memory reordering:
* Relaxed/weakly-ordered memory model: allows all types of memory reordering. 
	* Processor example: DEC Alpha
	* C11/C++11 low-level atomic operations also adopt this memory model.
* Weak with data dependency ordering memory model: all memory access, except data dependency ordering and LoadStore, can be reordered.
	* Processor example: ARM, PorwePC, Itanium(IA-64)
	* Linux RCU also relies on this assumption
* Stroing memory model: only StoreLoad can be reordered
	* Every machine instruction comes implicitly with acquire and release semantics.
	* When one CPU core performs a sequence of writes, every other CPU core sees those values change in the same order that they were written.
	* Processor example: x86/64, SPARC running in TSO (Total Store Ordering) mode
* Sequentially consistent memory model: no memory ordering
	* Software memory model for high-level programming languages (Java, C, C++).

How to prevent compiler reordering and processor reordering:
* A lightweight sync or fence instruction, reference [Acquire and Release Semantics](https://preshing.com/20120913/acquire-and-release-semantics/)
	* Acquire semantics prevent memory reordering of operations which follow it in program order
	* Release semantics prevent memory reordering of operations preceding it
* A full memory fence instruction, e.g. `smp_mb()`
* Memory operations which provide acquire or release semantics.

# Barriers

There are two major types of barriers:
* A compiler barrier prevents the compiler from moving code across the barrier.
* A memory barrier prevents the hardware from moving reads and writes across the barrier.
	* Weak or strong memory models determine what types of memory reordering to expect at runtime.

Any operation which acts as a memory barrier also prevents compiler reordering.
And on UP (uniprocessor), memory barriers provided by Linux Kernel (e.g. `smp_mp()`) are downgraded to compiler barriers.

A processor never sees its own memory effects out of order, even when threads are pre-empted and scheduled at arbitrary times.

Other barriers:
* data dependency barriers

# Types of Data Hazards

* Data-dependency -- Read-after-Write (RAW) Hazard
  * Also called flow dependency or true dependency
```
# r3 has data dependence
r3 <= r1 op r2
r5 <= r3 op r4
```
* Anti-dependency -- Write-after-Read (WAR) Hazard
```
# r1 has anti-dependence
r3 <= r1 op r2
r1 <= r4 op r5
```
* Output-dependency -- Write-after-Write (WAW) Hazard
```
# r3 has output-dependence
r3 <= r1 op r2
r3 <= r4 op r5
```

# Pure Function

A [pure function](https://en.wikipedia.org/wiki/Pure_function) has the following properties:
* The function return values are identical for identical arguments (no variation with local static variables, non-local variables, mutable reference arguments or input streams).
(同樣的參數輸入, 得到同樣的 return value, 且和 device I/O 無關)
	* Input operations undermine referential transparency
	* Output operations create side effects
* The function application has no side effects (no mutation of local static variables, non-local variables, mutable reference arguments or input/output streams).

An expression is called [referentially transparent](https://en.wikipedia.org/wiki/Referential_transparency) if it can be replaced with its corresponding value (and vice-versa) without changing the program's behavior.

An operation, function or expression is said to have a [side effect](https://en.wikipedia.org/wiki/Side_effect_(computer_science)) if it modifies some state variable value(s) outside its local environment, that is to say has an observable effect besides returning a value (the intended effect) to the invoker.
Examples of side effect:
* modifying a non-local variable
* modifying a static local variable
* modifying a mutable argument passed by reference
* performing I/O
* calling other side-effect functions

# Hazards

[Hazards](https://en.wikipedia.org/wiki/Hazard_(computer_architecture)) are problems with the instruction pipeline in CPU microarchitectures when the next instruction cannot execute in the following clock cycle,and can potentially lead to incorrect computation results.

Instructions in a pipelined processor are performed in several stages, so that at any given time several instructions are being processed in the various stages of the pipeline,
A hazard occurs when two or more of these simultaneous (possibly out of order) instructions conflict.

Types of hazards:
* Data hazards occur when instructions that exhibit data dependence modify data in different stages of a pipeline.
Ignoring potential data hazards can result in race conditions (also termed race hazards).
  * read after write (RAW, true dependency): This can occur because even though an instruction is executed after a prior instruction, the prior instruction has been processed only partly through the pipeline.
  * write after read (WAR, anti-dependency): represents a problem with concurrent execution.
  * write after write (WAW), an output dependency: may occur in a concurrent execution environment.
* Structural hazards occurs when two (or more) instructions that are already in pipeline need the same resource.
The result is that instruction must be executed in series rather than parallel for a portion of pipeline.
* Control hazards (branch hazards or instruction hazards) occurs when the pipeline makes wrong decisions on branch prediction and therefore brings instructions into the pipeline that must subsequently be discarded.


# Out-of-Order Execution (OoOE)

Out-of-order execution (or more formally dynamic execution) is not a bad thing.
It is a paradigm for pipelinging to make use of instruction cycles that would otherwise be wasted due to load stall.
In this paradigm, a processor executes instructions in an order governed by the availability of input data and execution units, rather than by their original order in a program.

Two cases:
* Load is stalled because of a miss in a cache (might have structueal hazards and data hazards)
* Path instructions are waiting for a branch condition to be computed (might have control hazards)

For case 1, out-of-order processors do the following things after instruction decode:
* Check for structural hazards, an instruction can be issued when a functional unit is available
* Check for data hazards, the instruction's operands have been calculated or loadded
* Execute a ready instruction if has no dependency with previous issued but not yet completed instructions

For case 2, speculation execution is applied.

# Speculative Execution

Speculative execution issue the instructions from the predicted path specculatively when going around a branch condition.
Speculative instructions can be executed before the branch, but are not committed until the branch condition is resolved.
* If the prediction was wrong, speculative instructions are flushed from the pipeline
* If prediction is right, instructions are no longer speculative

Speculative execution happens on a out-of-order pipeline microarchitecture.
For a in-ordier pipeline microarchitecture, instructions might be fetched speculative but are executed after branch

Besides speculative instructions can only be executed if
* must be safe: no additional exceptions or exceptions can be handled after the instruction is no longer speculative
* must generate the same results
